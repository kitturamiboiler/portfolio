한 줄 총평

결과물을 끝까지 연결하고 장애를 회귀 테스트로 남기는 힘은 좋지만, Vanilla JS → React 전환을 중간 상태로 오래 끌면서 DOM·전역 객체·문자열 HTML·CSS 덮어쓰기가 겹쳐 코드가 실제 규모보다 훨씬 어렵게 되어 있다.

코드가 “못 만든 코드”라기보다는 기능 추가 속도를 우선해 생긴 이행기 코드가 정리 시점을 놓친 상태에 가깝다. 지금은 동작하지만, 같은 방식으로 기능을 더 얹으면 다음 작업부터 수정 범위와 회귀 위험이 급격히 커진다.

잘한 것

1. API 경계를 한 곳에 모은 판단

static/js/api.js가 Browser API의 단일 진입점 역할을 한다. 공통 credentials, JSON 직렬화, 오류 모델, 401 리다이렉트, CSRF 발급과 1회 재시도까지 한 경계에 모은 것은 좋다. 각 화면에서 fetch를 제각각 쓰는 구조보다 훨씬 안전하다.

특히 다음 세부 판단이 좋다.

- CSRF 오류일 때만 토큰을 비우고 1회 재시도한다.

- URL path parameter에 encodeURIComponent를 꾸준히 사용한다.

- 204와 JSON/텍스트 응답을 공통 처리한다.

- AI 스트림도 공통 API 요청 경계를 통과시킨다.

2. 실패 상황을 “정상 제품 상태”로 다룸

테스트 이름만 봐도 단순 성공 경로보다 다음 상황을 많이 고려했다.

- 늦게 도착한 응답이 최신 상태를 덮지 않게 함

- 일부 API 실패에도 나머지 화면을 유지함

- 저장 실패 시 버튼 상태를 복구함

- 서버 계약 위반 값을 검증하거나 대체함

- 부분 성공과 보상 실패를 구분함

- 빈 결과와 조회 실패를 구분함

이건 실서비스 프론트에서 중요한 감각이다. “API가 항상 정상이고 순서대로 온다”는 가정에 기대지 않았다.

3. 접근성을 의식한 흔적이 넓게 퍼져 있음

aria-label, aria-live, role="status", role="alert", scope="row", 숨김 caption, focus-visible, prefers-reduced-motion 등이 여러 화면에 적용돼 있다. GameDialog에 Radix를 사용하고 애니메이션 감소 설정까지 연결한 것도 좋다.

접근성을 완성했다고 말할 수준은 아니지만, 나중에 억지로 붙인 흔적이 아니라 구현 과정에서 계속 생각한 코드다.

4. Storybook과 작업 기록을 적극적으로 사용함

31개의 Story가 있고, UI 결정과 사고 원인을 문서로 남겼다. 특히 Storybook과 운영 CSS가 어긋났던 사고를 테스트로 만든 것은 좋은 회고 방식이다. “왜 이 이상한 코드가 필요한가”를 주석과 문서로 남긴 점도 다음 사람이 맥락을 복원하는 데 도움이 된다.

5. 점진 전환 자체는 현실적인 선택이었음

기존 Spring MVC/Thymeleaf/Vanilla 기능을 전부 멈추고 React로 재작성하지 않고 island 방식으로 옮긴 것은 일정과 위험을 고려하면 합리적이다. React가 그리는 노드를 기존 JS가 직접 수정하지 않도록 이벤트로 넘긴 개선도 방향이 맞다.

6. 현재 기본 검증은 깨끗함

- npm run test:js: 200개 통과

- npm run build:home: 통과

- npm run build-storybook: 통과

즉, 현재 브랜치는 적어도 기존에 정의한 회귀 가드와 번들 생성 기준은 충족한다.

못한 것 / 실제로 위험한 것

P1. React 전환이 “임시 다리”에서 사실상 영구 구조가 됨

가장 큰 문제다. 현재 Home 상태는 대략 아래처럼 흐른다.

React가 DOM 생성
  → home.js가 querySelector로 다시 찾음
  → Vanilla controller가 상태 계산
  → window 전역 또는 CustomEvent로 React에 전달
  → React가 다시 그림

HomeStage는 window 이벤트를 구독하고, AiAssistantPanel은 React가 그린 캐릭터 DOM을 다시 querySelector한 뒤 MutationObserver로 감시한다. 오버레이는 home.js가 HTML 문자열을 만들고 React가 dangerouslySetInnerHTML로 주입한 뒤, 다시 home.js가 내부 DOM을 찾아 수정한다.

이 구조에서는 데이터 흐름을 이해하려면 React 컴포넌트, 전역 변수, 이벤트 이름, data-* 선택자, 기존 controller를 동시에 따라가야 한다. 작은 UI 변경도 여러 계층의 암묵적 계약을 깨뜨릴 수 있다.

다음에는: 기능 하나를 정해 끝까지 React 소유로 옮긴다. 예를 들어 진행 오버레이를 옮긴다면 마크업, 상태, API 호출 hook, 이벤트 처리를 한 번에 옮기고 기존 home.js 구현을 삭제한다. “껍데기만 React”인 기능을 더 만들면 안 된다.

P1. 실제 사용자 흐름 테스트가 거의 없음

JS 테스트 200개는 인상적이지만, 다수는 소스 파일을 문자열로 읽어 정규식이나 includes로 구조를 확인한다. 이런 테스트는 과거 버그의 재발 방지에는 유용하지만 다음은 보장하지 못한다.

- 버튼을 눌렀을 때 실제 화면이 바뀌는지

- 키보드 탭 순서와 포커스 복귀가 맞는지

- 오버레이에서 실제 API 성공/실패 UI가 맞는지

- 모바일 viewport에서 겹치거나 잘리는지

- Story가 브라우저에서 오류 없이 상호작용하는지

Storybook Vitest 설정은 있지만 package.json에 이를 명확히 실행하는 스크립트가 없고, 접근성 설정도 test: "todo"라 위반이 CI 실패로 이어지지 않는다. 이번 로컬 환경에서 vitest run은 브라우저 서버 bind 권한 문제로 실제 Story 테스트를 시작하지 못했다.

다음에는: 핵심 사용자 흐름 5개만 먼저 Playwright로 만든다. 로그인 후 홈 진입, 타이머 시작/정지, 오버레이 열기/닫기, 커뮤니티 작성, 관리자 센서 저장 정도면 효과가 크다. Storybook 접근성은 고칠 수 있는 Story부터 error로 올린다.

P1. 수동 캐시 버전 관리가 배포 실수를 부름

번들 entry 이름은 home-app.js, manager-sensors-app.js처럼 고정이고, 일부 화면만 ?v=20260902-7 같은 값을 손으로 갱신한다. 관리자 번들은 버전 query조차 없다. 내용이 바뀌어도 CDN/브라우저가 기존 entry를 재사용할 가능성이 있다.

내부 chunk에는 hash가 있어도, 그 chunk를 가리키는 고정 entry 파일이 캐시되면 새 hash를 알 수 없다.

다음에는: Vite manifest를 생성하고 Thymeleaf가 manifest의 hashed entry를 읽게 하거나, 빌드 시 버전 값을 자동 주입한다. 사람이 날짜 문자열을 올리는 절차는 없앤다.

P2. 파일 크기가 책임의 크기를 그대로 보여 줌

대표적으로 다음 파일이 너무 크다.

- home.js: 약 1,499줄

- spaceRoom.js: 약 1,479줄

- SensorWorkspace.jsx: 약 1,028줄

- studyRecords.js: 약 1,177줄

- home.css: 약 3,779줄

- home-overlay-theme.css: 약 2,550줄

- managerDashboard.css: 약 2,007줄

긴 파일 자체가 죄는 아니지만, 이 파일들은 실제로 여러 책임을 가진다. 예를 들어 home.js는 초기화, 데이터 변환, HTML 템플릿, 오버레이 라우팅, 이벤트 위임, 커뮤니티 CRUD, 진행 화면 조립까지 맡는다. SensorWorkspace.jsx도 차트, 목록, 편집, 임계값, 여러 modal을 한 파일에 둔다.

다음에는: 줄 수 기준이 아니라 feature 기준으로 자른다. community/, progress/, sensor/chart, sensor/devices, sensor/thresholds처럼 상태와 UI를 함께 이동한다. 단순히 helper만 별도 파일로 빼는 식의 쪼개기는 효과가 작다.

P2. 문자열 HTML과 innerHTML 사용 범위가 너무 넓음

프로젝트 전체에서 innerHTML 계열 대입이 약 49곳이다. 서버/사용자 값을 escapeHtml로 처리하려는 노력은 보이지만, 누락 한 번이 XSS로 이어지는 구조다. 더 큰 문제는 문자열 템플릿이 타입·이벤트·접근성 검사를 모두 우회한다는 것이다.

dangerouslySetInnerHTML의 입력을 “검증된 내부 템플릿”이라고 주석으로 보장하지만, 실제 템플릿에는 API 응답값이 섞인다. 현재 눈에 띄는 곳은 많이 escape되어 있어 즉시 취약점이라고 단정할 수는 없지만, 안전성이 코드 구조가 아니라 개발자의 매번 정확한 escape에 의존한다.

다음에는: 새 기능에서는 문자열 HTML을 금지하고 JSX 또는 DOM API의 textContent를 쓴다. 당장 남겨야 하는 경계에는 DOMPurify 같은 sanitizer와 Trusted Types 적용을 검토한다.

P2. 모달 구현이 두 체계라 접근성 품질이 다름

도움말/설정은 Radix GameDialog를 쓰지만 나머지 Home overlay는 직접 만든 role="dialog"이고, 퇴실 확인창도 innerHTML로 즉석 생성한다. Escape 처리는 있으나 일반 overlay와 확인창에는 완전한 focus trap이 없고, 배경 콘텐츠 inert 처리도 일관되지 않다.

다음에는: 모든 modal/overlay를 GameDialog 한 경계로 합친다. 화면 모양이 달라도 focus trap, Escape, 초기 포커스, 포커스 복귀, 배경 inert는 같은 primitive가 맡아야 한다.

P2. CSS가 이미 덮어쓰기 경쟁 상태임

CSS 전체에 !important가 약 324개이고, 500줄이 넘는 CSS 파일이 16개다. Home 한 화면이 여러 CSS 파일을 순서 의존적으로 로드하고, Storybook도 그 순서를 수동 복제한다. 이것은 스타일 시스템이 캡슐화되지 않았고 cascade 충돌을 override로 해결해 왔다는 신호다.

Storybook CSS 동기화 테스트는 좋은 응급조치지만, 복잡한 로드 순서 자체를 없애지는 못한다.

다음에는: 새 CSS는 cascade layer(@layer reset, tokens, components, pages, utilities)를 정하고, 컴포넌트 단위 스타일 파일의 소유권을 하나로 만든다. 기존 !important는 화면별로 한꺼번에 지우지 말고, 이관하는 feature에서만 제거한다.

P2. AI SSE 파서에 경계 조건 누락이 있음

aiAssistantClient.js는 \n\n만 프레임 경계로 보고, stream 종료 후 decoder tail과 buffer를 flush하지 않는다. 서버가 CRLF(\r\n)를 쓰거나 마지막 event 뒤에 빈 줄을 붙이지 않으면 마지막 답변 조각이 유실될 수 있다.

또한 drawer를 닫아 기존 요청을 abort한 직후 다시 열어 새 요청을 보내면, 이전 요청의 finally가 abortControllerRef.current = null을 실행해 새 controller 참조를 지울 수 있는 경쟁 조건이 있다.

다음에는: SSE parser를 독립 모듈로 만들고 chunk 분할, CRLF, 다중 data:, 마지막 미종결 frame, abort/reconnect를 단위 테스트한다. controller를 비울 때도 if (ref.current === controller) 조건을 둔다.

아쉬운 것

1. 공통 UI를 만들었지만 실제 화면이 완전히 따르지는 않음

GameButton, GameDialog, GameTabs, PanelHeader 같은 좋은 primitive가 생겼지만, 기존 화면에는 같은 역할의 독자 버튼·dialog·tab 구현이 많이 남아 있다. 디자인 시스템이 “있는 것”과 “쓰이는 것” 사이에 간격이 있다.

2. 린트·포맷·타입 검사가 없음

ESLint, Prettier, TypeScript/checkJs 같은 정적 품질 장치가 없다. 실제 코드에서도 import spacing, indentation, quote가 섞여 있다. 동작 문제는 아니지만 리뷰 비용을 높이고, nullable 응답이나 event payload 실수를 컴파일 전에 잡지 못한다.

추천 순서: Prettier → ESLint의 오류 규칙만 → checkJs/JSDoc 또는 신규 feature부터 TypeScript. 기존 전체를 한 번에 엄격하게 바꾸지 않는다.

3. 의존성 분류와 정리가 덜 됨

phaser는 소스 import/사용처가 확인되지 않아 현재로서는 불필요해 보인다. 반대로 빌드 도구인 Vite와 React plugin은 runtime dependencies, 실제 컴포넌트가 import하는 prop-types는 devDependencies에 있어 의도가 뒤섞여 있다. latest 버전도 재설치 시 예측 가능성을 낮춘다.

4. 정적 자산이 저장소와 배포를 무겁게 함

정적 디렉터리 약 65MB 중 BGM이 약 61MB다. 오디오는 사용자가 재생할 때만 내려받겠지만, 저장소 clone/이미지 build/배포 artifact에는 계속 포함된다.

다음에는: 오디오는 object storage/CDN으로 분리하거나 최소한 별도 asset pipeline과 장기 캐시 정책을 둔다. 라이선스와 출처도 manifest에 연결한다.

5. 주석이 훌륭하지만 코드 복잡도를 대신 설명하는 경우가 많음

사고 배경을 자세히 적은 주석은 장점이다. 다만 “한쪽만 바뀌면 깨진다”, “순서가 반드시 같아야 한다”, “양쪽 DOM 소유권이 충돌한다”는 주석이 반복되는 것은 구조가 취약하다는 증거이기도 하다. 다음 리팩토링 목표는 주석을 더 잘 쓰는 것이 아니라 그런 경고가 필요 없는 계약을 만드는 것이다.

놓친 것

1. 성능 예산

Home entry는 약 181.8KB, 공통 client chunk는 약 192.9KB(각 gzip 약 59~60KB)다. 현재 아주 위험한 크기는 아니지만, bundle budget이나 측정 자동화가 없어 기능을 추가할수록 조용히 커질 수 있다. Web Vitals, route별 초기 JS, 이미지/오디오 로딩 정책에 대한 기준도 보이지 않는다.

2. 관측 가능성

화면 오류는 주로 toast와 console.error 수준에서 끝난다. 실제 사용자가 어느 API/화면에서 실패했는지 수집하는 frontend error telemetry, request ID 연계, 성능 측정이 없다. API error에 requestId를 이미 담고 있으므로 UI 오류 리포팅까지 연결하기 좋다.

3. 명확한 마이그레이션 종료 조건

문서에는 React 이관의 다음 단계가 있지만, 언제 home.js를 없앨지, 어떤 기능 순서로 옮길지, 신규 기능에 무엇을 금지할지 완료 조건이 없다. 그래서 임시 bridge가 자연스럽게 영구 API가 됐다.

4. 브라우저 호환 기준

inert, crypto.randomUUID, MutationObserver, dynamic import, 최신 React/Vite를 사용하지만 지원 브라우저 기준과 polyfill 정책이 명시되지 않았다. 내부 서비스라 최신 Chromium만 지원한다면 그것도 문서로 고정하는 편이 낫다.

다음 작업에서 바로 바꿀 규칙

1. 새 기능은 React와 Vanilla 중 한쪽만 DOM을 소유한다. React가 만든 노드를 외부에서 querySelector해 수정하지 않는다.

2. 새 UI에 문자열 HTML을 쓰지 않는다. 사용자/API 값이 들어가는 UI는 JSX로 렌더링한다.

3. 모달은 하나의 primitive만 쓴다. GameDialog를 확장해 모든 overlay에 사용한다.

4. 한 PR에서 기능 구현과 전체 CSS 보정을 섞지 않는다. feature CSS만 수정한다.

5. 버그 수정에는 실제 동작 테스트를 최소 1개 붙인다. 문자열 가드는 보조 테스트로만 둔다.

6. entry cache busting은 빌드가 한다. 날짜 query를 사람이 바꾸지 않는다.

7. 500줄을 넘긴 파일은 무조건 분리하는 게 아니라 책임 목록을 리뷰한다. 책임이 3개 이상이면 feature 단위로 나눈다.

8. 접근성 위반을 점진적으로 CI 오류로 올린다. 새 Story부터는 todo 예외를 허용하지 않는다.

권장 리팩토링 순서

1단계: 안전망 (1~2일)

- ESLint/Prettier 도입

- test:storybook 스크립트와 CI 실행 경로 명시

- 핵심 Playwright smoke test 3~5개 추가

- bundle size 기록 및 상한 설정

2단계: 위험한 경계 제거 (2~4일)

- AI SSE parser 보강 및 단위 테스트

- 모든 Home overlay를 GameDialog 기반으로 통일

- Vite manifest 기반 hashed entry 적용

- 사용하지 않는 phaser 검증 후 제거

3단계: feature 단위 React 이관 (기능별 진행)

추천 순서는 progress → community → study records → space/team이다. 상대적으로 독립적인 진행 화면부터 이관해 패턴을 만든 뒤, CRUD와 외부 controller 결합이 큰 기능으로 간다.

각 feature의 완료 조건은 다음과 같다.

- 해당 기능의 HTML 문자열 생성 삭제

- 해당 기능의 home.js event delegation 삭제

- API adapter + state hook + React view로 구성

- loading/empty/error/success browser test 추가

- 기존 CSS override 감소

최종 판단

우리 프론트의 강점은 예외 상황을 실제로 고민하고, 한번 겪은 장애를 테스트와 문서로 남긴 것이다. 약점은 그때그때의 안전장치가 누적돼 전체 구조가 너무 많은 암묵적 계약을 갖게 된 것이다.

따라서 다음 목표는 새 프레임워크나 화려한 재설계가 아니다. 이미 시작한 React 이관을 feature 단위로 끝내고, 한 상태·한 DOM·한 modal·한 build source라는 단순한 소유권을 회복하는 것이 가장 효과가 크다.
