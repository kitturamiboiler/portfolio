1. 프로젝트 개요

Omagotchi는 교육 기수에 참여하는 사용자가 출석, 학습 시간, 퀘스트, 캐릭터 성장, 공간 이용과 커뮤니티 활동을 하나의 웹 서비스에서 경험하도록 만드는 프로젝트다. 초기에는 기능의 전체 범위를 빠르게 확인하기 위해 데스크톱 운영체제와 게임 UI를 섞은 프로토타입을 제작했다. 이후 실제 사용 흐름을 점검하면서 단순히 기능이 존재하는 것보다 사용자가 무엇을 먼저 보고, 어떤 행동을 해야 하는지 즉시 이해하는 것이 더 중요하다는 결론에 도달했다.

2. 최초 프로토타입

Omagotchi

2.1 처음 설정한 화면 구조

최초 프로토타입은 웹 브라우저 안에 하나의 가상 데스크톱을 만드는 방식이었다.

- 시작 화면

- 사용자 로그인 및 회원가입

- 관리자 로그인 및 관리자 등록

- 캐릭터 선택 화면

- 홈 화면과 개인 정보 오버레이

- 실습실 화면

- 타이머와 학습 기록

- 퀘스트와 설정

- 기수 가입 및 관리자 대시보드

- 하단 앱 Dock와 앱 아이콘

실습실 화면에는 Finder, Terminal, VS Code, IntelliJ, GitHub, 데이터베이스, 노트, 타이머 등 직접 제작한 앱 아이콘을 배치했다. 이 단계는 서비스에 필요한 기능과 에셋을 한 화면에서 확인하는 데 의미가 있었다.

2.2 초기 프로토타입의 장점

- 서비스가 다루려는 기능 범위를 빠르게 시각화했다.

- Pixel Tool로 캐릭터, 앱 아이콘, Dock을 직접 제작하여, 실습실이라는 고유한 콘셉트를 확보했다.

- 사용자 화면과 관리자 화면이 모두 필요하다는 점을 조기에 확인했다.

- 출석, 타이머, 퀘스트, 공간처럼 서로 연결되는 기능을 한 번에 검토할 수 있었다.

2.3 V1 화면 구조 상세 분석

이 시기의 화면은 모두 V1에서 검토한 초기 정보 구조와 인터랙션 시안으로 분류한다. 구현 완성도를 평가하기보다 어떤 가설을 세웠고, 실제 서비스에 적용하기 어려운 이유가 무엇이었는지 기록하는 것이 목적이다. KDT 특성상 가장 자주 보는 화면이 노트북인 만큼 노트북을 실제 웹 사이트 내에서 제작하여 보기 편한 UI를 제공하려 하였으나, 별도의 모니터를 연결하지 않으면 화면이 그렇게 크지 않을 뿐더러 개발하는 사람 입장에선 이 버튼이 무엇을 의미하는지에 대한 상세적인 정보를 알고 있었으나 처음 이 화면을 접하는 사용자에게는 도움말도 없고, 막말로 로그인해서 캐릭터 선택후 막 들어와서 뭐 어쩌라고? 라는 식의 화면이었다.

홈 화면 대안 1

[이미지: ]

- 캐릭터를 중앙에 두고 실습실·퀘스트·랭크·뱃지 기능을 화면 가장자리에 배치했다.

- 화면 중앙의 캐릭터를 강조하려는 의도는 명확했지만, 사용자의 현재 상태와 다음 행동이 여러 위치로 분산되었다.

- 실습실, 퀘스트, 랭크, 뱃지가 동일한 형태의 버튼으로 보여 기능의 중요도와 현재 상태를 구분하기 어려웠다.

- 랭크와 뱃지처럼 조회 성격이 강한 정보도 실행 버튼처럼 보여 상호작용 가능 범위를 오해할 수 있었다.

- logo.png 는 프로토타입을 위한 로고의 위치일 뿐이다.

- 캐릭터에 비해 화면의 빈 영역이 크고, 출석과 학습 시작이라는 핵심 행동이 보이지 않았다.

홈 화면 대안 2

[이미지: ]

- 사용자 프로필과 경험치, 오늘의 퀘스트, 캐릭터, 실습실 이동을 하나의 화면에 배치했다.

- 대안 1보다 정보가 모였지만, 프로필·퀘스트·캐릭터·이동 버튼이 서로 다른 방향에 놓여 시선이 반복적으로 이동했다.

- 오늘의 퀘스트가 화면의 많은 면적을 사용하지만 실제 학습 시작이나 출석 행동과 직접 연결되지 않았다.

- 실습실로 이동이 유일하게 큰 버튼이어서 서비스의 핵심이 학습 기록인지 공간 이동인지 불분명했다.

- 캐릭터가 성장 상태를 전달하는 주체라기보다 화면 중앙을 채우는 장식에 가까웠다.

햄버거 메뉴

[이미지: ]

- 출석 체크, 랭크, 뱃지, 도감, 설정, 도움말을 2열 아이콘 메뉴로 구성했다.

- 메뉴 수를 감추어 홈을 단순하게 만드는 장점은 있었지만, 사용자가 메뉴를 열기 전까지 주요 기능을 발견하기 어렵다.

- 출석처럼 매일 가장 먼저 사용해야 하는 기능이 햄버거 메뉴 안에 들어가 접근 단계가 늘어났다.

- 아이콘만으로 랭크·뱃지·도감의 차이를 즉시 이해하기 어렵고, 기능 간 우선순위도 드러나지 않았다.

- 모바일 메뉴 패턴을 넓은 데스크톱 화면에 그대로 사용해 남는 공간을 제대로 활용하지 못했다.

설정 화면

[이미지: ]

- 좌측 목록과 우측 콘텐츠를 나누는 전통적인 설정 레이아웃을 고려했다.

- 내 정보 조회·수정, 탈퇴 확인, 로그아웃이 한 영역에 모여 있었으나 일상 설정과 위험한 계정 작업의 구분이 부족했다.

- 항목 수에 비해 패널이 지나치게 커서 빈 공간이 크게 남았다.

- 로그아웃은 화면 하단에 작게 배치되어 발견하기 어렵고, 탈퇴는 일반 메뉴와 같은 수준으로 보여 위험도가 표현되지 않았다.

- 설정이 별도 창인지 전체 페이지인지 불분명해 다른 화면과 전환 규칙이 맞지 않았다.

Dock 기반 네비게이션

[이미지: ]

- Finder, Terminal, VS Code, IntelliJ, GitHub, Note, Timer 등 직접 만든 앱 아이콘을 Dock에 배치했다.

- 개발 실습실이라는 분위기와 에셋 제작 성과를 보여주는 데는 효과적이었다.

- 반면 사용자는 아이콘이 Omagotchi 내부 기능인지 외부 도구 실행 버튼인지 구분하기 어렵다.

- 서비스의 기능 분류가 출석·학습·기수·공간이 아니라 운영체제 애플리케이션의 은유에 종속되었다.

- 아이콘 수가 늘수록 가로 공간을 많이 차지하고, 작은 화면에서는 잘리거나 축소되어야 했다.

- 현재 위치, 선택 상태, 알림 상태를 Dock만으로 일관되게 표현하기 어려웠다.

- 브라우저 안에 운영체제 Dock를 다시 만드는 구조라 웹 서비스와 가상 데스크톱의 조작 체계가 충돌했다.

[이미지: ]

- 데이터베이스 등의 기능을 다시 폴더 안에 묶는 구조를 검토했다.

- 폴더 분류는 개발 도구 기준이어서 사용자의 학습 목적이나 업무 흐름을 설명하지 못했다.

- 기능이 늘어날수록 폴더와 아이콘을 어디에 배치할지에 대한 새로운 규칙이 계속 필요했다.

2.4 배포된 omagotchi.site UX 분석

분석 범위: 공개 접근이 가능한 시작 화면, 사용자 로그인·회원가입, 기수 관리자 로그인·등록 화면을 기준으로 확인했다.

유지할 수 있는 장점

- 시작 화면에서 시작하기 행동 하나를 강조해 첫 진입의 선택지가 명확하다.

- 로고, 캐릭터, 어두운 배경을 반복 사용해 V1 화면보다 브랜드 인상이 일관적이다.

- 사용자 인증과 관리자 인증의 진입 경로가 분리되어 있다.

- 입력 항목에 시각적 라벨과 접근 가능한 이름이 제공되어 기본적인 폼 구조는 이해하기 쉽다.

- 시작, 로그인, 회원가입 화면이 같은 2단 카드 구조를 사용해 화면 간 시각적 연속성이 있다.

시작 화면의 문제

[이미지: ]

- 로고, 나만의 오마고치를 키워보세요, 서비스 설명이 비슷한 내용을 반복해 정보 밀도에 비해 세로 공간을 많이 사용한다.

- 처음 방문한 사용자가 출석·학습·캐릭터 성장 중 무엇을 실제로 할 수 있는지 구체적으로 알기 어렵다.

- 캐릭터와 말풍선이 크지만 핵심 CTA와의 관계가 약해, 장식과 행동 영역이 분리되어 보인다.

- 서비스 미리보기나 사용 흐름이 없어 시작하기 이후 어떤 과정이 이어지는지 예측하기 어렵다.

로그인·회원가입의 문제

[이미지: ]

[이미지: ]

- 화면 제목은 Login, Register인데 입력 라벨과 버튼은 한국어여서 언어 체계가 혼합되어 있다.

- 로그인 화면의 비밀번호 변경은 로그인 전 사용자의 목적과 맞지 않는다. 이 위치에서는 비밀번호 찾기 또는 비밀번호 재설정이 더 정확하다.

- 회원가입 화면에 비밀번호 조건, 이메일 형식, 사용자 이름 규칙과 오류 처리 예시가 보이지 않는다.

- 비밀번호 표시·숨김, 입력 오류, 로딩, 제출 불가 상태와 같은 실제 폼 상태를 사용자에게 설명할 장치가 부족하다.

- 왼쪽 브랜드 패널이 넓어 폼보다 강하게 보이며, 인증이라는 핵심 작업에 집중되는 공간은 상대적으로 작다.

[이미지: ]

- Manager Login, Manager Register와 한국어 폼이 혼용되어 사용자 인증 화면과 같은 언어 규칙을 따르지 않는다.

- 이거 코드 AI 돌리시는거 아니죠?, 안 보는 것 같아도 다 보입니다! 문구는 일시적인 재미는 있지만 공식 관리자 화면의 신뢰성과 서비스 톤을 해칠 수 있다.

- 기수 관리자, 시스템 관리자 등 역할 범위에 대한 설명 없이 관리자라는 표현만 사용해 어떤 사용자가 가입해야 하는지 불명확하다.

- 소속 기관을 자유 입력으로 받으면 같은 기관이 다른 표기로 중복될 수 있고, 담당 기수와 승인 주체의 관계도 설명되지 않는다.

- 관리자 등록이 즉시 완료되는지, 시스템 관리자 승인이 필요한지 화면에서 알 수 없다.

- 사용자 로그인 화면과 관리자 로그인 화면의 차이가 캐릭터와 문구에 집중되어 있고, 실제 권한 범위와 책임은 드러나지 않는다.

배포 화면에서 확인된 개선 기준

- 인증 화면 제목과 버튼 언어를 한국어로 통일한다.

- 시작 화면의 중복 문구를 줄이고 서비스의 실제 행동을 짧게 설명한다.

- 인증 폼에서는 입력 조건, 오류, 로딩, 비활성 상태를 명시한다.

- 관리자용 재미 문구는 신뢰를 해치지 않는 범위로 조정한다.

- 기수 관리자는 시스템 전체 관리자가 아니라 담당 기수 운영자임을 가입 전부터 설명한다.

- 소속과 역할은 자유 입력보다 서버의 승인·배정 흐름을 기준으로 설계한다.

- 캐릭터는 큰 장식으로만 두지 않고 폼 상태, 성공, 오류에 반응하는 피드백 요소로 활용한다.

3. 구현하면서 발견한 문제

3.1 웹 안에 또 다른 화면을 만든 구조

[이미지: ] 브라우저 안에 운영체제 창을 다시 구성하면서 실제 웹 서비스가 사용할 수 있는 공간이 줄었다. 화면 안의 프레임, 창 테두리, Dock가 콘텐츠보다 강하게 보였고, 사용자는 웹 페이지를 사용하는지 가상 데스크톱을 조작하는지 판단하기 어려웠다. 특히 작은 노트북 화면에서는 콘텐츠가 잘리거나 브라우저 배율을 90%로 줄여야 전체 화면이 보이는 문제가 발생했다.

3.2 사용자의 시선 우선순위 부족

초기 홈 화면에는 타이머, 출석, 캐릭터, 네비게이션, 퀘스트, 각종 앱 기능이 비슷한 크기로 배치되었다. 기능은 많았지만 사용자가 접속한 직후 해야 할 행동이 명확하지 않았다.

- 입실 전인데 입실 버튼이 먼저 눈에 들어오지 않은 문제

- 기능 버튼이 모두 동일한 중요도로 표현되는 문제

- 출석 상태와 캐릭터 성장이 서로 분리되어 보이는 문제

- 버튼의 의미를 하나씩 눌러 봐야지 만 알 수 있는 버튼들의 존재

3.3 일관되지 않은 화면 전환

일부 메뉴는 새 페이지로 이동하고 일부 메뉴는 오버레이로 열렸다. 도움말, 진행, 내 정보, 기수, 기록, 공간, 설정처럼 홈의 맥락을 유지해야 하는 기능까지 별도 화면으로 이동해 사용 흐름이 끊겼다.

3.4 고정 크기 중심의 레이아웃

픽셀 단위의 큰 크기와 고정 여백이 많아 외부 모니터에서는 빈 공간이 크게 남고 맥북에서는 하단 콘텐츠가 잘렸다. 브라우저 확대 비율에 따라 캐릭터와 경험치 바의 위치도 달라졌다.<br>캐릭터나 Gamification 을 고집하고 검증된 절차 없이 무작정 만들기만 한 것도 문제가 되었다.

3.5 역할 모델의 혼선

[이미지: ] 초기 관리자 화면에서는 ADMIN, GLOBAL_ADMIN, MANAGER의 책임 범위가 명확하지 않았다. 기수 관리자 등록 화면에서 운영기관과 담당 기수를 어떻게 입력해야 하는지, 기수 생성과 관리자 지정 권한이 누구에게 있는지 화면만으로 설명되지 않았다. 논의 결과 현재 서비스에서는 다음 기준으로 정리했다.

원문 표
역할책임 범위
시스템 관리자전체 기수와 기수 관리자 지정 등 최상위 운영
기수 관리자자신이 배정된 기수의 교육생, 가입 신청, 코드, 출결, 센서 확인
사용자기수 가입, 출석, 학습, 공간 이용, 커뮤니티 참여

기수 관리자는 모든 기수와 모든 센서를 조회하지 않으며, 관리자 지정 기능도 갖지 않는다.

4. 요구사항과 데이터 구조 재검토

UI를 다시 만들기 전에 화면 이름이 아니라 사용자의 행동을 기준으로 기능을 정리했다.

- 기수 목록을 조회한다.

- 가입 코드를 입력해 기수 참가를 신청한다.

- 기수 관리자가 신청을 승인하거나 거절한다.

- 사용자가 입실과 퇴실을 기록한다.

- 학습 타이머로 학습 시간을 기록한다.

- 실습실은 출석 후 자동 입장한다.

- 회의실과 도서관은 사용, 참여, 연장, 반납 상태를 관리한다.

- 퀘스트 조건을 달성하고 보상을 수령한다.

- 관리자는 자신이 담당한 기수의 센서와 출결만 확인한다.

이 과정에서 화면 Controller 이름에 맞춰 API를 만드는 것이 아니라 /api/cohorts, /api/cohorts/{id}/join-codes, /api/cohort-memberships/{id}/approve처럼 자원과 행동 중심으로 연결해야 한다는 기준도 세웠다.

5. 레퍼런스 검토

Habitica, Nuku, Octodoro 등을 검토했고, 특히 Octodoro의 다음 특징이 현재 서비스와 잘 맞았다. Habitica - Gamify Your Life Octodoro \| Gamified Study Timer Nuku - Gamified Study Timer

- 홈에서 가장 중요한 타이머에 집중한다.

- 캐릭터가 단순 장식이 아니라 진행 상태의 중심에 있다.

- 부가 기능은 오버레이로 열어 홈의 맥락을 유지한다.

- 퀘스트, 업적, 랭킹, 통계가 하나의 진행 화면에 묶인다.

- 큰 화면을 사용하지만 콘텐츠 폭과 시선 흐름은 제한한다.

- 버튼과 캐릭터가 즉각적으로 반응해 게임 같은 조작감을 제공한다.

레퍼런스를 그대로 복제하지 않고 Omagotchi의 핵심인 교육 기수, 출결, 실습 공간과 센서를 결합하는 방향으로 재해석했다.

6. 리빌딩 원칙

1. 브라우저 전체를 서비스 화면으로 사용한다.

2. 홈의 첫 행동은 입실과 학습 시작으로 제한한다.

3. 부가 메뉴는 홈 위 오버레이로 통일한다.

4. 캐릭터를 화면의 중심 피드백 장치로 사용한다.

5. 기수와 공간 정보는 사용자의 소속 범위만 보여준다.

6. 색상보다 명암과 상태 차이로 정보를 구분한다.

7. 노트북과 외부 모니터에서 모두 사용할 수 있도록 반응형으로 구성한다.

8. 백엔드 연결 전에도 화면 상태를 검증할 수 있게 구성하되, 임시 상태와 실제 서버 상태를 구분한다.

색상을 선택했을 때 본문 글자까지 해당 색으로 바꾸는 시도는 정보 전달을 방해해 제외했다. 선택 여부는 테두리와 체크 상태로만 표현했다.

7.4 홈

[이미지: ] 홈은 타이머, 출석, 캐릭터 성장의 관계가 한눈에 보이도록 재구성했다.

- 상단에 한 줄 네비게이션 유지

- 중앙에 학습 타이머와 시작·기록 버튼 배치

- 입실 전에는 입실하기를 명확한 주요 행동으로 표시

- 캐릭터 이름, 상태 점, 레벨 표시

- 선택한 GIF 캐릭터와 말풍선 표시

- 경험치 바와 다음 레벨까지 필요한 XP 표시

- 캐릭터 부유 모션과 클릭 반응 적용

- 타이머 실행 시 브라우저 탭 제목에도 남은 시간 표시

- 캐릭터를 반복 클릭하면 반응 문구가 바뀌고, 과도하게 클릭하면 잠시 그만 눌러!를 표시한 후 카운트를 초기화하도록 구성했다.

7.5 Home Down과 출석

[이미지: ] 홈 아래쪽은 별도 페이지가 아니라 같은 페이지에서 스크롤로 이어진다. 상단 타이머 영역과 구분되도록 정보 밀도와 배경을 조정했다.

- 오늘 입실·퇴실 및 지각·조퇴 정보

- 실제 연·월을 기준으로 생성되는 출석 달력

- 토요일과 일요일 구분

- 연속 출석 정보

- 불필요한 타이머로 돌아가기 버튼 제거

출석의 기준 날짜와 최종 판정은 서버 데이터가 기준이 되어야 하며, 프론트의 로컬 상태는 프로토타입 검증용으로만 사용한다.

7.6 진행

[이미지: ] 퀘스트, 업적, 랭킹, 타임라인, 통계를 하나의 진행 오버레이 안에 구성했다. 초기 레퍼런스의 파란색은 전체 서비스 팔레트와 충돌해 Omagotchi 색상 체계로 다시 조정했다. 퀘스트 달성 시 수령 버튼, 수령 완료 상태와 네비게이션 알림 점을 구분했다. 실제 요구사항에 없는 코인 보상은 제거하고 XP 중심으로 정리했다.

7.7 공간

[이미지: ] LAB, MEETING ROOM, LIBRARY를 같은 공간 오버레이의 탭으로 구성했다.

- 실습실: 출석 후 자동 입장, 온도·습도·CO₂와 참여 인원 표시

- 회의실: 사용 가능, 사용 중, 참여, 알림, 연장, 반납 상태 표시

- 도서관: 사용 가능, 사용 중, 입장 및 퇴장 상태 표시

실습실에는 선택한 캐릭터와 말풍선을 함께 표시하고, 회의실·도서관에서는 내가 사용 중인 공간을 테두리와 상태 문구로 강조했다.

7.8 기수

[이미지: ] 현재 참여 중인 기수와 가입 가능한 기수를 구분한다. 가입 코드를 입력해 참가 신청을 할 수 있도록 설계했으며, 참여 중인 기수 정보는 내 정보에도 함께 표시되도록 연결했다.

7.9 커뮤니티

[이미지: ] 커뮤니티는 공지와 자유 게시판을 중심으로 구성했다.

- 전체·공지·자유 탭

- 제목과 본문 검색

- 고정 공지 우선 표시

- 게시글 작성·수정·삭제

- 댓글과 좋아요

- 첨부 상태

- 페이지네이션

- 글쓰기는 연필 아이콘으로 표현

실시간 채팅은 게시판 안에 넣기보다 홈에서 실습실, 회의실, 기수 채팅으로 빠르게 전환하는 구조가 더 적절하다고 판단했다. 단, 실시간 기능은 현재 MVP 범위와 백엔드 구현 상황에 맞춰 추후 확정한다.

7.10 설정

[이미지: ] 홈에 있던 별도 밝기 슬라이더는 제거하고 설정 오버레이로 이동했다. 밝기 설정은 배경뿐 아니라 오버레이에도 동일하게 반영되도록 범위를 통일했다.

- 화면 밝기

- 비밀번호 변경 오버레이

- 로그아웃

로그인 상태를 유지한 채 시작 화면으로 돌아가는 기능은 사용자 의미가 불명확해 제거했다.

7.11 기수 관리자

- 담당 기수 출결 조회

- 담당 기수 실습실 센서 확인

전체 기수 생성과 기수 관리자 지정은 시스템 관리자 책임이므로 기수 관리자 대시보드에서 제외했다.

7.12 오류 화면

[이미지: ] 기본 서버 오류 화면 대신 Omagotchi 캐릭터를 활용한 404, 403, 500 커스텀 페이지를 구성했다. 경로 오류, 접근 권한 부족, 서버 오류의 의미와 다음 행동을 각각 다르게 안내한다.

8.1 CSS 구조 분리

하나의 CSS 파일에 모든 화면 스타일을 넣지 않고 화면과 역할별로 분리했다.

- 인증 화면

- 홈

- 캐릭터 선택

- 공간

- 진행

- 관리자 인증

- 관리자 대시보드

- 오류 화면

- 게임 폰트

공통 규칙은 재사용하고 화면 전용 규칙은 각 파일에서 관리하도록 경계를 정리했다.

8.2 상태 표현

백엔드 연결 전 프로토타입에서는 localStorage와 JavaScript 상태를 이용해 다음 흐름을 검증했다.

- 선택 캐릭터와 색상

- 캐릭터 레벨과 경험치

- 퀘스트 보상 수령

- 화면 밝기

- 출석 화면 상태

이 데이터는 최종 진실의 원천이 아니며, API 연결 후 서버 응답으로 교체할 수 있도록 화면 갱신 지점을 분리했다.

2026년 7월 27일 view 프로젝트를 localhost:8082에서 실행하고 시작 화면, 캐릭터 선택, 홈, 진행 오버레이, 공간 오버레이, 기수 관리자 로그인과 대시보드를 직접 확인했다. 아래 내용은 Figma 시안만 비교한 것이 아니라 현재 로컬에서 실제로 렌더링되는 화면과 DOM 구조를 기준으로 정리했다.

- 확인 경로: /, /characterSelector, /home, 홈의 진행·공간 오버레이, /managerLogin, /managerDashboard

- 확인 항목: 첫 행동의 명확성, 내비게이션 구조, 캐릭터 피드백, 출석·학습 연결, 공간 상태, 관리자 권한 범위

- 주의 사항: 백엔드 API 연동 전이므로 출석, XP, 기수, 센서와 커뮤니티 데이터는 화면 흐름 검증을 위한 임시 상태가 포함되어 있다.

9.2 V1 문제를 현재 구현에서 바꾼 방식

시작 화면: 분할형 소개 화면 → 하나의 진입 행동

V1 문제

- 브라우저 안에 다시 카드형 창을 만들고 좌우를 나누면서 서비스보다 레이아웃 프레임이 먼저 보였다.

- 로그인, 캐릭터, 서비스 설명 중 무엇이 첫 단계인지 한눈에 알기 어려웠다.

- 관리자와 사용자 진입의 중요도가 비슷하게 보일 가능성이 있었다.

현재 변경

- 브라우저 전체를 초록색 격자 배경으로 사용하고 Omagotchi, 캐릭터, 짧은 설명, 시작하기만 중앙에 배치했다.

- 사용자 주 행동은 큰 버튼 하나로 제한하고 기수 관리자 로그인은 하단 텍스트 링크로 분리했다.

개선 결과

- 처음 접속한 사용자의 시선이 브랜드 → 캐릭터 → 설명 → 시작하기 순서로 이동한다.

- 별도 창을 해석하지 않고 바로 사용자 흐름에 진입할 수 있다.

캐릭터 선택: 작은 미리보기 → 선택 결과를 이해할 수 있는 게임 화면

V1 문제

- 캐릭터 미리보기와 팔레트가 작고, 선택한 캐릭터의 이름·성격·색상 정보를 충분히 설명하지 못했다.

- 캐릭터 선택이 단순 에셋 고르기로 보였고 함께 성장할 대상을 정한다는 의미가 약했다.

현재 변경

- 왼쪽에 선택 캐릭터를 크게 표시하고 머리 위 말풍선을 배치했다.

- 오른쪽에서 8종 캐릭터와 8종 색상을 선택하며, 현재 캐릭터 이름·색상명·설명을 함께 제공한다.

- 선택 상태는 글자색 변경 대신 테두리와 눌림 상태로 구분하고, PNG 썸네일 선택 결과를 GIF 미리보기와 홈에 연결한다.

개선 결과

- 사용자는 선택 결과를 확정하기 전에 캐릭터의 외형과 정보를 함께 비교할 수 있다.

- 캐릭터 선택이 이후 홈 경험과 이어지는 초기 설정 단계로 바뀌었다.

홈 내비게이션: Dock·햄버거 혼용 → 라벨이 있는 한 줄 메뉴와 오버레이

V1 문제

- Dock 아이콘이 내부 기능인지 외부 개발 도구인지 모호했다.

- 햄버거 메뉴 안에 출석 같은 핵심 기능이 들어가 발견성이 낮았다.

- Dock, 햄버거, 화면별 버튼이 같은 기능을 중복 제공했다.

현재 변경

- 도움말, 진행, 내 정보, 기수, 기록, 공간, 커뮤니티, 설정을 텍스트 라벨이 있는 한 줄 메뉴로 고정했다.

- 부가 기능은 홈을 떠나지 않고 같은 화면 위의 오버레이로 연다.

- 활성 메뉴와 알림 여부를 별도 상태로 표현한다.

개선 결과

- 아이콘의 의미를 추측하지 않아도 되고 현재 홈 맥락을 유지한 채 다른 정보를 확인할 수 있다.

- 운영체제 Dock 은유에서 서비스 기능 중심 정보 구조로 전환했다.

핵심 행동: 여러 기능의 동일한 강조 → 타이머와 입실 우선

V1 문제

- 실습실 이동, 퀘스트, 랭크, 뱃지 등이 같은 중요도로 보여 접속 직후 해야 할 일이 불명확했다.

- 입실, 학습 시작, 기록이 서로 다른 화면과 장치 UI에 흩어져 있었다.

현재 변경

- 홈 중앙에 학습 타이머와 시작, 기록, 입실하기를 연속 배치했다.

- 입실 상태에 따라 버튼을 입실하기 → 퇴실하기 → 퇴실 완료로 변경한다.

- 타이머 실행 시간은 브라우저 탭 제목에도 반영한다.

개선 결과

- 사용자가 접속 후 출석을 기록하고 학습을 시작하는 순서를 화면만으로 이해할 수 있다.

- 별도 비모 타이머 장치 UI 없이 실제 행동과 상태를 한 영역에서 관리한다.

캐릭터: 중앙의 정적 장식 → 행동에 반응하는 상태 피드백

V1 문제

- 캐릭터가 화면 중앙을 채웠지만 출석·학습·보상과의 관계가 보이지 않았다.

- 성장 게임을 표방해도 실제 반응이 없어 장식 요소에 가까웠다.

현재 변경

- 선택한 캐릭터와 색상을 홈에서 유지하고 눈 깜빡임 GIF를 표시한다.

- 캐릭터 이름, 온라인 상태 점, 레벨, XP 바와 다음 레벨 조건을 한 묶음으로 제공한다.

- 타이머 시작·일시정지, 클릭 횟수와 레벨업에 따라 움직임과 말풍선 문구가 바뀐다.

개선 결과

- 사용자의 행동에 캐릭터가 즉시 반응해 학습 기록과 게임 경험이 연결된다.

- 성장 수치가 캐릭터 근처에 있어 레벨 변화의 이유를 추적하기 쉬워졌다.

출석 정보: 분산된 카드 → 홈 아래 연속 대시보드

V1 문제

- 입실 완료 카드, 타이머, 구간 기록이 서로 떨어져 있어 하루 학습 상태를 한 번에 보기 어려웠다.

- 출석 기록과 연속 출석의 시간 범위가 명확하지 않았다.

현재 변경

- 홈 아래로 스크롤하면 오늘 입실·퇴실·조퇴·지각, 월별 달력, 연속 출석이 이어서 나타난다.

- 달력은 실제 연·월과 요일을 계산하고 주말을 구분한다.

- 별도 타이머로 돌아가기 버튼 없이 같은 페이지의 위아래 흐름으로 연결한다.

개선 결과

- 학습 행동과 그날의 출석 결과를 한 페이지에서 연속적으로 확인할 수 있다.

- 월별 기록과 스트릭이 오늘 출석의 보조 정보로 재배치되었다.

진행 정보: 퀘스트·랭크·뱃지 분산 → 진행 오버레이로 통합

V1 문제

- 퀘스트, 랭크, 뱃지가 홈·햄버거·프로필에 반복되어 어디에서 확인해야 하는지 모호했다.

- 보상 가능과 수령 완료 상태가 충분히 구분되지 않았다.

현재 변경

- 퀘스트, 업적, 랭킹, 타임라인, 통계를 하나의 진행 오버레이 탭으로 통합했다.

- 퀘스트별 진행 바, 현재 값, XP, 보상 받기와 수령 완료 상태를 제공한다.

- 받을 보상이 있으면 홈 메뉴에 알림 상태를 표시한다.

개선 결과

- 성장과 관련된 조회·보상 기능의 위치가 하나로 정리되었다.

- 사용자는 달성 여부뿐 아니라 지금 수행할 행동까지 확인할 수 있다.

공간: 가상 실습실과 Dock → 목적별 공간 상태

V1 문제

- 실습실 장면과 앱 Dock가 공간을 많이 차지했지만 실제 이용 상태를 전달하지 못했다.

- 회의실·도서관 이용과 실습실 센서 정보가 같은 서비스 흐름으로 정리되지 않았다.

현재 변경

- 공간 오버레이 안에서 실습실, 회의실, 도서관을 탭으로 전환한다.

- 실습실은 CO₂·온도·습도·참여 인원과 캐릭터 상태를 표시한다.

- 회의실과 도서관은 사용 가능, 참여, 사용 중, 연장, 반납 상태를 카드에서 구분한다.

개선 결과

- 공간 화면의 목적이 데스크톱 꾸미기에서 실제 공간 상태 확인과 이용 행동으로 바뀌었다.

- 사용자가 선택한 캐릭터와 말풍선을 유지해 홈과 공간의 게임 경험도 이어진다.

설정: 큰 독립 창 → 홈 안의 시스템 조정 오버레이

V1 문제

- 항목 수에 비해 설정 창이 지나치게 컸고 빈 공간이 많았다.

- 일반 설정, 로그아웃, 탈퇴 같은 계정 행동의 위험도가 구분되지 않았다.

현재 변경

- 설정을 홈 오버레이로 열고 화면 밝기, 비밀번호 변경, 로그아웃처럼 현재 필요한 기능만 남겼다.

- 밝기 설정은 홈 배경뿐 아니라 오버레이까지 동일한 범위로 반영한다.

- 비밀번호 변경도 별도 페이지 이동 대신 현재 맥락 안에서 처리하도록 구성했다.

개선 결과

- 설정을 위해 홈 흐름을 벗어나지 않고, 불필요하게 큰 빈 패널도 줄였다.

기수 관리자: 전체 관리자처럼 보이는 화면 → 담당 기수 운영 화면

V1 문제

- ADMIN, GLOBAL_ADMIN, MANAGER가 혼재해 기수 관리자의 실제 책임 범위를 알기 어려웠다.

- 관리자 등록에서 운영기관과 담당 기수를 직접 입력하도록 하면 승인·배정 책임이 불명확했다.

- 모든 기수와 관리자 지정 기능이 한 대시보드에 포함될 가능성이 있었다.

현재 변경

- 기수 관리자 로그인에서 일반 계정과 동일한 이메일 인증을 사용하되 활성 관리자 소속이 있는 기수만 보인다고 설명한다.

- 대시보드의 기수 선택 목록은 배정받은 기수로 제한한다.

- 운영 요약, 가입 코드, 참가 신청, 소속, 출결, 공간·센서, 커뮤니티, 작업 이력으로 메뉴를 구성한다.

- 시스템 관리자의 책임인 전체 기수 생성과 관리자 지정 기능은 제외했다.

개선 결과

- 관리자가 접속했을 때 자신의 담당 범위와 오늘 처리할 업무를 바로 확인할 수 있다.

- 교육생 수, 승인 대기, 오늘 출석, 센서 상태가 실제 운영 작업 단위로 재구성되었다.

오류 상태: 기본 서버 오류 → 서비스 문맥을 유지하는 오류 화면

V1 문제

- 예외 상황을 고려한 화면이 없어 오류 발생 시 브라우저나 서버의 기본 페이지로 서비스 경험이 끊길 수 있었다.

현재 변경

- 403, 404, 500 화면을 분리하고 Omagotchi 캐릭터와 상황별 안내, 다음 행동을 제공한다.

개선 결과

- 정상 흐름을 벗어나도 서비스의 시각 언어와 복구 경로를 유지한다.

12. 회고

최초 프로토타입은 완성된 UX라기보다 서비스의 기능 범위와 콘셉트를 빠르게 확인하기 위한 설계였다. 직접 만든 앱 아이콘, 캐릭터, Dock와 실습실 화면은 이후 리빌딩에서도 버려진 작업이 아니라 Omagotchi의 시각적 정체성과 기능 목록을 정의하는 기초가 되었다. 가장 큰 변화는 화면을 예쁘게 다시 그린 것이 아니다. 기능 중심 화면에서 사용자 행동 중심 화면으로 기준을 바꾼 것이다.

- 사용자가 접속하면 가장 먼저 입실 상태를 확인한다.

- 학습을 시작하면 타이머와 캐릭터가 반응한다.

- 학습 결과가 퀘스트와 경험치에 반영된다.

- 필요한 부가 기능은 현재 맥락을 유지한 채 오버레이로 확인한다.

- 기수 관리자에게는 자신이 담당한 범위만 제공한다.

리빌딩을 통해 Omagotchi는 단순한 기능 모음이나 가상 데스크톱에서 벗어나, 출석과 학습 행동이 캐릭터 성장으로 이어지는 교육용 게임 서비스라는 방향을 갖게 되었다.
