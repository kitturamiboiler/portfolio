# [ADR] Home UI - React Island 기반 유동형 웹앱 스테이지 도입

## 1. 상태 (Status)

- [ ] 제안됨 (Proposed)
- [x] 수용됨 (Accepted)
- [ ] 거절됨 (Rejected)
- [ ] 폐기됨/대체됨 (Deprecated/Superseded)

## 2. 배경 및 맥락 (Context)

기존 Home 화면은 데스크톱 기준의 HUD 배치를 중심으로 구성되어 있었다. MacBook 또는 넓은 데스크톱 화면에서는 크게 어색하지 않았지만, 화면 폭과 높이가 조금만 바뀌어도 상단 메뉴, 타이머, 캐릭터, 하단 HUD, 도크 버튼이 서로 다른 기준으로 움직이며 UI가 쉽게 깨졌다.

특히 모바일 세로 화면, 모바일 가로 화면, 태블릿 화면, 브라우저 창을 대각선으로 조절하는 상황에서는 특정 기기 크기별 보정만으로는 안정적인 레이아웃을 만들기 어렵다. 새 기기가 나올 때마다 CSS breakpoint를 추가하는 방식은 유지보수성이 낮고, Home 화면의 웹앱 성격에도 맞지 않는다.

따라서 Home 화면을 기기별 페이지가 아니라 하나의 유동형 웹앱 stage로 보고, UI를 컴포넌트 단위로 관리할 수 있는 구조가 필요했다.

## 3. 고려한 대안 (Alternatives)

기존 Vanilla JS와 CSS만 유지 — 기존 Thymeleaf HTML과 `home.js` 구조를 그대로 두고 `responsive.css`에서 breakpoint를 추가해 화면별 깨짐을 보정한다.

모바일 전용 Home 경로 유지 — `/mobile/home` 같은 별도 화면을 계속 발전시켜 모바일에서는 별도 Home UI를 보여주고, PC에서는 기존 `/home`을 유지한다.

Home 전체 React 전환 — Home 화면의 UI와 기존 기능 로직을 모두 React 상태와 컴포넌트로 다시 작성한다.

React Island 도입 — Spring MVC, Thymeleaf, 인증, 기존 기능 JS는 유지하되, Home의 주요 UI DOM만 React 컴포넌트가 렌더링하게 한다. 기존 `home.js`가 의존하는 `data-*` DOM 계약은 그대로 보존한다.

## 4. 결정 사항 및 사유 (Decision & Rationale)

결정: React Island 도입 방식을 사용한다.

Home 화면의 상단 메뉴, BGM 패널, 재실 인원 HUD, 타이머 패널, 캐릭터 stage, 경험치 HUD, 채팅 바, 도크 버튼을 React 컴포넌트로 분리한다. 다만 기존 타이머, 캐릭터, 경험치, 출석, BGM, 재실 인원, 오버레이 동작은 즉시 React 상태로 재작성하지 않는다.

React 컴포넌트는 기존 `home.js`가 찾는 `data-*` 속성을 그대로 가진 DOM을 렌더링한다. 또한 React 번들은 기존 `home.js`보다 먼저 로드되어, `home.js`의 초기 `querySelector`가 정상적으로 동작하도록 한다.

이 방식을 선택한 이유는 다음과 같다.

기존 Vanilla JS와 CSS만 유지하는 방식은 단기 수정은 빠르지만, 화면 비율이 바뀔 때마다 새 보정 규칙이 늘어나는 문제가 있다. 이미 `responsive.css`에 여러 breakpoint 보정이 누적되어 있고, 이는 장기적으로 예측하기 어려운 레이아웃 충돌을 만든다.

모바일 전용 Home 경로를 유지하는 방식은 PC와 모바일 Home이 서로 다른 화면으로 갈라진다. Home은 서비스의 핵심 화면이므로 기능 표현과 상태 흐름이 둘로 나뉘면 유지보수 비용이 커질 가능성이 높다.

Home 전체를 React로 전환하는 방식은 가장 깔끔해 보일 수 있지만, 기존 `home.js`에 이미 타이머, 캐릭터, 출석, BGM, 오버레이 로직이 들어 있어 한 번에 옮기면 변경 범위가 과도하게 커진다.

React Island 방식은 UI 구조를 컴포넌트화하면서도 기존 기능 동작을 그대로 활용할 수 있다. 따라서 현재 피처 브랜치에서 현실적으로 적용 가능한 중간 단계다.

## 5. 결과 및 영향 (Consequences)

### 장점 (Positive)

Home UI를 상단 메뉴, 타이머, 캐릭터, HUD, 도크 같은 의미 단위로 분리할 수 있다.

기존 기능 로직을 한 번에 React로 재작성하지 않아도 된다.

기존 Spring MVC, Thymeleaf, 인증, 세션 구조를 유지할 수 있다.

기존 `home.js`의 `data-*` 기반 DOM 연결을 유지하므로 기능 회귀 위험을 줄일 수 있다.

이후 타이머 상태, 오버레이 상태, 레이아웃 모드 같은 부분을 점진적으로 React 상태로 옮길 수 있다.

Home 화면을 `/home` 단일 진입점으로 유지하면서 화면 비율 대응을 개선할 수 있다.

### 단점 (Negative)

React와 기존 Vanilla JS가 한 화면에서 공존하므로, 초기에는 두 방식의 경계 관리가 필요하다.

React가 렌더링하는 DOM 구조가 기존 `home.js`의 `data-*` 계약을 깨면 기능이 바로 동작하지 않을 수 있다.

React 번들 로드 순서가 중요해진다. React 번들이 기존 `home.js`보다 늦게 실행되면 `home.js`가 필요한 DOM을 찾지 못할 수 있다.

Vite, React, npm 의존성이 프로젝트에 추가된다.

Home UI가 React로 분리되었지만, 기능 상태는 아직 기존 JS에 남아 있어 완전한 React 구조는 아니다.

## 6. 규정 준수 (Compliance)

인증, 인가, JWT, 세션, 로그인 성공 흐름은 변경하지 않는다.

Home React Island는 프론트 표현 계층 변경으로 제한한다.

기존 `home.js`가 사용하는 `data-*` 속성은 임의로 제거하거나 이름을 바꾸지 않는다.

React 번들은 기존 `home.js`보다 먼저 로드한다.

Home 화면은 특정 기기 모델 기준으로 구현하지 않는다.

레이아웃은 화면 비율, 가용 폭, 가용 높이, 안전 영역을 기준으로 설계한다.

새 breakpoint를 추가할 때는 특정 기기 대응이 아니라 레이아웃 모드 대응인지 먼저 확인한다.
